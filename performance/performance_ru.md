# Производительность клиента

## Асинхронность: конвейеризируйте futures

Все вызовы возвращают `CompletableFuture`. Последовательный `.get()` после каждого
вызова превращает клиента в синхронного и теряет до 10–20× пропускной:

```java
// плохо
for (var k : keys) cache.get(k).get();

// хорошо
var futures = keys.stream().map(cache::get).toList();
for (var f : futures) f.get();
```

## Сжатие payload

- Значения больше порога сжатия (по умолчанию **1024 байта**) сжимаются на клиенте
  и разжимаются прозрачно.
- Порог настраивается при создании клиента. На мелких значениях сжатие не работает —
  оверхеда нет.
- Если ваша нагрузка — много значений 1–4 КБ, подберите порог под свои данные.

## Хинты роутинга

- `KeyHintData`, возвращаемый из `create*`, стоит сохранять и передавать в последующие
  вызовы — клиент не пересчитывает хэш и не ходит за топологией лишний раз.
- В кластере хинт — это ещё и явный placement связанных ключей в одну партицию.

## Таймауты

- У каждого вызова есть `timeout` (по умолчанию из настроек клиента). Для чтений под
  нагрузкой ставьте короткий таймаут и ретрайте — это защищает p99 лучше, чем долгое
  ожидание.

## Большие контейнеры

- `getContainer` и чтение больших коллекций идут стримингом батчами — не дёргайте
  гигантские контейнеры целиком в горячем пути; лучше диапазоны
  (`getElementInRangeOrderedSet` и т.п.).

## Серверные рычаги (кратко)

- CPU pinning потоков (конфиг ноды) убирает джиттер планировщика.
- Снапшоты — фоновые, hot path не трогают.
- Бенчмарки и методика измерения: таб Performance на сайте / `operations`.
