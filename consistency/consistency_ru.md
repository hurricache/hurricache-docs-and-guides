# Гарантии консистентности

Модель HurriCache: **per-partition single-owner**. Каждая партиция имеет ровно одного
владельца (master) и одну реплику (RF=2). «Active-Active» означает отсутствие
standby-нод: каждая нода обслуживает трафик и владеет частью партиций. Это НЕ
multi-master записи в один ключ.

## Что гарантируется

| Свойство | Гарантия |
|---|---|
| Подтверждение записи | Клиент получает ответ после применения операции владельцем партиции |
| Репликация | Изменения доставляются на реплику асинхронно, упорядоченными батчами; отставание наблюдаемо (`replication_queue_pending_commands{target}`) |
| Консистентность | Записи в один ключ сериализуются владельцем; конфликты разрешаются версионированием и клиентскими метками времени |
| Окно потери данных | Если владелец падает до доставки изменения на реплику, изменение может быть потеряно — окно ограничено лагом репликации |
| Восстановление | При отказе владельца реплика автоматически промоутится после stability window; RF=2 восстанавливается фоновой миграцией |

## Версионирование

Каждый ключ несёт `(version, timestamp)`:

- `version` — монотонный счётчик мутаций ключа;
- `timestamp` — время мутации. Источник: metadata `x-hc-client-ts-bin` (часы клиента,
  GMT-0) либо время прибытия для старых клиентов. Часы клиентов и серверов должны
  быть синхронизированы (NTP).

Правила применения на реплике:

- Скалярные перезаписи (`CREATE_VALUE`, `UPDATE_VALUE`, `SET_TTL`) — LWW по timestamp:
  устаревшая команда отбрасывается.
- Остальные команды — дедупликация по version: команда с `stored_v >= cmd_v` пропускается.
- `ADD_TO_TAIL`, `ADD_TO_FRONT`, `ATOMIC_ADD`, `ATOMIC_SUB` — применяются всегда
  (конкурентные операции с двух нод легитимны); метадата реплики подтягивается до
  `max(stored, cmd)`.
- Локи и `REMOVE` — без версионных проверок.

## Stale write: честное отклонение опоздавших записей

Если запрос задержался сетью, а ключ уже изменён более поздней записью
(`stored_ts > client_ts`), сервер отклоняет его с `ABORTED` и обоими временами в тексте.
Это защита от перезаписи новых данных, а не сбой: клиент решает — перечитать и повторить
или отказаться. Подробности: [../error-handling](../error-handling).

## Восстановление стейта (state restore)

Если реплика отклонила команду (рассинхрон состояния), отправитель не повторяет дельту —
он читает актуальное значение ключа и шлёт полный слепок (`restore=true`): реплика
пересоздаёт значение целиком. Дельты не накапливаются, расхождение версий самоустраняется.

## Модель отказов

1. Координатор детектирует отказ ноды (heartbeat).
2. Выдерживается stability window (конфиг, десятки секунд) — короткие рестарты не
   вызывают ложных миграций.
3. Нода исключается, реплики её партиций промоутятся, маршрутизация перестраивается;
   клиенты получают новую топологию автоматически.
4. Фоновая миграция восстанавливает RF=2 на оставшихся нодах без остановки клиентов.
5. Снапшоты на диск пишутся в фоне (по времени/числу изменений) и используются при
   рестарте ноды. Автоматическое восстановление кластера из снапшотов — roadmap,
   не готовая функция.

## Чего модель НЕ обещает

- **Не strong consistency** в общем случае: чтение с реплики может отдавать данные
  с отставанием на величину лага. Чтение с владельца — актуальное.
- **Не zero data loss**: окно потери равно лагу асинхронной репликации.
- Tie при равных timestamp (две записи с двух нод в одну миллисекунду) — разрешается
  владельцем партиции; глобального порядка между нодами для одного ключа в этой
  ситуации не гарантируется (закрывается клиентскими ts + владением ключом).
