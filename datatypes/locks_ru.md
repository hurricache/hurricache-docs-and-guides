# Локи (READ / WRITE / GLOBAL)

Локи — первоклассные операции API над любым объектом (скаляр или контейнер), привязанные
к клиенту-владельцу. Доступны только в типизированном gRPC API (через RESP-коннектор
локов нет).

## Уровни

| Уровень | Чтение | Запись | Ближайший паттерн Redis |
|---|---|---|---|
| `READ` | все клиенты читают параллельно | только владелец | нет аналога — GET не лочит |
| `WRITE` | только владелец | только владелец | SET NX EX, но без различения чтение/запись |
| `GLOBAL` | только владелец | только владелец | в Redis нет клиентских глобальных локов |

## Java API

| Метод | Что делает |
|---|---|
| `lock(key, hint, level, lockTtlSeconds, clientId, timeout)` → `LockStatus` | Взять лок уровня READ/WRITE/GLOBAL; `lockTtlSeconds` — время блокировки в секундах, по истечении лок снимается автоматически |
| `unlock(key, hint, clientId, timeout)` → `LockStatus` | Снять лок (только владелец) |

## Правила

- **TTL лока и TTL данных — разные сущности.** У лока свой TTL **в секундах**,
  независимый от TTL объекта. По истечении времени блокировка **снимается
  автоматически** — объект разблокируется, но данные не удаляются и остаются доступными.
- **Только владелец управляет локом**: никто другой не может ни снять его, ни изменить
  параметры (в отличие от `DEL` ключа SET NX EX, который может снять кто угодно).
- **Атомарный апгрейд READ → WRITE**: повышение уровня — одна операция без окна гонки;
  никто не может вклиниться между снятием и повторным взятием.
- Лок работает и для скаляров, и для контейнеров (очередь можно залочить целиком
  на время пакетной обработки).

## Применение

- Критические секции над составным состоянием (несколько полей контейнера).
- Координация воркеров: READ-лок на время чтения с гарантией неизменности, апгрейд до
  WRITE для изменения.
- Защита очереди/карты на время пакетной операции.
