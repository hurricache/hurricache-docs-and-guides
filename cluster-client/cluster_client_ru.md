# Cluster-aware клиент

Cluster-aware (smart) клиент сам знает топологию кластера: подключается к любой ноде,
получает таблицу маршрутизации от координатора и дальше направляет каждый ключ сразу
владельцу партиции — без релеев.

## Режимы чтения/записи (`Mode`)

| Режим | Поведение |
|---|---|
| `MASTER` | Операции только на мастере партиции |
| `MASTER_THAN_BACKUP` | Сначала мастер; при его недоступности — реплика |
| `BACKUP` | Только реплика (чтение с реплики для разгрузки мастера) |
| `LB_SMART` | Балансировка между мастером и репликой |

Режим переключается на лету: `client.setMode(Mode.BACKUP)` возвращает клиент для
цепочки вызовов.

## Топология и роутинг

- Клиент получает `RoutingInfo` (таблицу партиция → нода) от координатора и обновляет её
  при изменениях кластера.
- Слот ключа: `weak_hash % partitions` (количество партиций — из конфигурации кластера).
- При сбое мастера клиент прозрачно ретраит на реплику; при смене топологии таблица
  обновляется автоматически.

## Placement: KeyHintData

`KeyHintData.of(strongHash, weakHash)` позволяет задать weak hash ключа явно.
Ключи с одинаковым weak hash гарантированно попадают в одну партицию (одну ноду) —
так делают локальность связанных данных (например, все ключи заказа рядом).

Хинт возвращается из `create*` и потом передаётся в последующие вызовы — клиент
не пересчитывает хэш и не трогает сеть лишний раз.

### Явные хинты: задавайте оба хэша полностью или доверьтесь серверу

`KeyHintData` переключает хэширование из режима «управляет сервер» в режим
«управляет клиент» — для **обоих** хэшей, гибридного режима нет:

- **strongHash — идентичность.** По умолчанию движок вычисляет его из ключа.
  Задавайте свой, если ваши ключи — непрозрачные идентификаторы (например, бинарные
  токены) и хэш движка — не то, с чем вы хотите сверяться.
- **weakHash — placement.** Партиция = `weak_hash % partitions`. Одинаковый weak hash
  для связанных ключей → одна партиция, одна нода (паттерн ex-hash-tag, но явный).

- **Без хинта (по умолчанию):** сервер сам выводит оба хэша из ключа и держит партиции
  сбалансированными. Промахи маршрутизации разрешаются прозрачно (relay или
  `FAILED_PRECONDITION` с `x-fastcache-route`). `NOT_FOUND` всегда значит ровно одно:
  ключа не существует.
- **С явным хинтом:** сервер полностью доверяет переданному и ничего не
  пере-маршрутизирует и не пере-хэширует. Несовпадение strongHash или неверный weak hash
  читается как `NOT_FOUND` — нода ничего не нашла там, куда вы указали, и нигде больше
  искать не будет.

`NOT_FOUND` под явным хинтом поэтому двусмыслен: ключа может не быть — или хэши неверны.
Диагностика: повторите вызов без хинта. Если ключ нашёлся — виноват хинт.

Правило большого пальца: если вы управляете хэшами для набора ключей — управляйте ими
до конца: каждое чтение и запись этих ключей несёт один и тот же хинт. Смешение
доступа с хинтом и без для одних и тех же ключей — баг приложения, а не сервера.

> Redis: хэш-теги спрятаны внутри строк ключа. HurriCache: явный типизированный
> параметр placement.

## Standalone vs cluster-aware

| | `FastCacheAsyncStandaloneClient` | Smart client |
|---|---|---|
| Топология | одна нода | таблица маршрутизации |
| Сбой ноды | ошибка клиенту | прозрачный retry на реплику |
| Интерфейс | `HurriCacheClientInterface` — один и тот же | тот же |

Переход standalone → кластер не требует изменения прикладного кода: меняется только
создание клиента.
