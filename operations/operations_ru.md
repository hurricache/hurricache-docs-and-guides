# Эксплуатация

## Метрики Prometheus

- Нода экспортирует метрики на `cache_stat_port` (по умолчанию 8080), путь `/metrics`.
- Готовые дашборды Grafana в [../dashboards](../dashboards) — подхватываются compose-примером автоматически, либо импортируйте вручную:
  - `fastcache-overview.json` — обзор кластера (throughput, latency, память, партиции)
  - `fastcache-scalars.json` — скалярные операции, атомики и локи
  - `fastcache-containers.json` — жизненный цикл контейнеров, head/tail, позиционные и map/set операции
  - `fastcache-replication.json` — глубина очереди репликации по target, throughput sender/receiver, ошибки
  - `fastcache-resp.json` — операции RESP-коннектора по семействам данных
  - `fastcache-client-api.json` — вызовы smart client / relay по типам операций
- Compose-пример поднимает Prometheus + Grafana вместе с кластером:
  [../cluster-compose](../cluster-compose).

Что смотреть в первую очередь:

| Метрика | О чём говорит |
|---|---|
| латентности операций (avg/p99 по операциям) | деградация hot path |
| размер кэша / число ключей | рост данных, давление на память |
| счётчики снапшотов | частота и длительность фоновых сбросов |
| ошибки по операциям | проблемы клиентов/типов |
| статус лицензии | печатается в потоке статистики stdout |
| `replication_queue_pending_commands{target}` (gauge) | Команд репликации в очереди к каждой ноде. Рост = реплика отстаёт/недоступна; главный алерт отставания реплики |
| `cache_partition_last_snapshot_ts{partition}` (gauge) | Время (epoch мс) последнего снапшота партиции. Отставание от текущего времени при активной записи — снапшоты не успевают |

Снапшот партиции штампуется **в начале** сериализации, поэтому
`cache_partition_last_snapshot_ts` одновременно задаёт водную линию для инкрементальной
миграции (в разработке): при восстановлении ноды будут пересылаться только ключи,
изменённые после этого времени.

## Снапшоты

- Два триггера, оба настраиваются: по времени (`interval`, по умолчанию 300 с) и по числу
  изменений в партиции (`change_threshold`, по умолчанию 1000).
- Снапшоты фоновые — не влияют на hot path запросов.
- Файлы пишутся в `storage_directory`; при рестарте нода восстанавливает данные из них.
- Проверка: записать ключ, перезапустить контейнер, прочитать — ключ на месте.

## Кластерная эксплуатация

- Добавление ноды — один вызов координаторского API (автоматизируется по HTTP).
- Замена ноды «горячая»: данные копируются внутри кластера.
- Stability window 30–120 с поглощает короткие рестарты без ложных миграций — p99
  не дёргается при деплоях.
- Кластер из трёх нод поднимается меньше чем за минуту.

## CPU pinning

- Секция `cpu_pinning` в конфиге: явные списки ядер для каждой группы потоков —
  `cache_workers_cpu_ids`, `replication_server_workers_cpu_ids`,
  `replication_client_workers_cpu_ids`, `redis_proxy_workers_cpu_ids` и
  `defer_deleter_cpu_id`. Ядра задаются через запятую (`"0,1,2"`) или YAML-списком;
  пустой список — без пиннинга; потоков больше ядер — раскладка по кругу.
  Подробности — в `server-config/server_config_ru.md`.
- **`HURRICACHE_WORKER_CORES`** (env, например `HURRICACHE_WORKER_CORES=1,2,3`):
  пинит **внутренние потоки gRPC event engine** (worker threads библиотеки) на
  перечисленные ядра. Сервер при старте печатает подтверждение в лог.
  Используйте, чтобы отделить сетевой стек gRPC от рабочих потоков кэша.

## Лицензии

- Без файла лицензии действуют community-лимиты: до 3 нод, 1024 партиции, 2 рабочих
  потока на ноду.
- Лицензия — Ed25519-подписанный YAML, привязанный к fingerprint конфигурации кластера;
  проверяется при старте, лицензионный сервер не нужен.
- После истечения — 30-дневный soft-период с теми же лимитами, затем возврат к
  community-лимитам. Без внезапных остановок.
- Подробности формата: `doc/licensing.md` в репозитории сервера.
