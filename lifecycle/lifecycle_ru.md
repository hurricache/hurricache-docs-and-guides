# TTL и жизненный цикл

## Три независимых механизма времени

| Механизм | Единицы | Что делает по истечении |
|---|---|---|
| TTL данных (`setTtl`) | миллисекунды | объект становится протухшим и удаляется |
| TTL лока (`lock`) | секунды | блокировка снимается автоматически; данные не трогаются |
| окно стабильности кластера | секунды (30–120) | короткий рестарт ноды без миграций |

## TTL данных

- Назначается при создании (`create*(..., ttlMs, ...)`) или позже через
  `setTtl(key, ttlMs)`; прочитать — `getTtl(key)`.
- TTL вешается на объект целиком: у контейнера один TTL на все элементы.
- Снятие TTL (persist): `setTtl` со значением «без истечения».
- Протухший объект при чтении выглядит как отсутствующий (`NOT_FOUND`) — физическое
  удаление происходит фоновой зачисткой, это не видно клиенту.

## TTL лока

- У лока своё время жизни в секундах, не связанное с TTL данных.
- Истёкший лок снимается сам: объект разблокируется, данные остаются.
- Поэтому лок безопасно брать «на всякий случай» — зависший клиент не заблокирует
  данные навсегда.

## Удаление и его отложенность

- `remove` / `pop` / истечение TTL — логическое удаление сразу, физическое — с
  небольшой отсрочкой (чтобы читатели, уже держащие ссылку, корректно завершили).
- Для клиента это прозрачно: после `remove` ключ сразу не виден.

## Правила большого пальца

- Всегда задавайте TTL для сессионных/временных данных — кэш сам о себе позаботится.
- Не используйте TTL данных как замену локу и наоборот: они решают разные задачи.
